# RCA: 26-minute meeting lost entirely - Python backend wedged before its read loop (16 Jul 2026)

_Investigation 16 Jul 2026 (Claude), read-only. No product code changed. Evidence
(`backend.log`, `meeting.json`) copied into this folder from the meeting folder before
it is processed/trashed. Line numbers under "backend.log" refer to the copy here; code
`file:line` refs are against repo HEAD `45e5ff8`._

**Severity: total data loss.** The whole meeting `2026_07_16 - heiko` (~26 min, 09:33:07 -> 09:59:16 UTC) reached disk as nothing. The `audio/` folder is empty, all three transcript files are 0 bytes, `segment_count=0`. Unlike the 6 Jul and 8 Jul incidents (which lost a channel or a tail), this one captured **zero audio from t=0**.

---

## 1. Incident summary

- Backend command (backend.log:3): `.venv/bin/python -m diarise_transcribe.muesli_backend --emit-meters --transcribe-stream both --output-dir ".../2026_07_16 - heiko/audio" --keep-wav --live-asr-only`
- Input = DJI "Wireless Mic Rx" (USB, id=168); output = MacBook Pro Speakers (id=121). No pinning, follow mode.
- Swift side looked healthy the entire meeting: `engine.start.ok`, `mic.first-frame`, continuous heartbeats with `engineAlive=true`, `frames` climbing to ~14484, `micLevel` 0.001-0.027.
- **`ui.storm ... transcript_rows=0` from minute 1 to the end** - the live transcript never gained a row.
- At Stop: `engine.stop` (backend.log:717), then a `listener.*` storm as the **output** device flipped MacBook Pro Speakers -> Bose QC35 II (Bluetooth) - the user put the headphones on around Stop. Then `Backend did not exit after stop; terminating.` (:734) and a staging-folder line (:735).
- `meeting.json`: `status=completed`, `duration_seconds=1569.89` (= wall-clock 26m9s), `segment_count=0`, `last_timestamp=0`, empty `speaker_names`.

Same morning, Muesli had been `pkill -9`'d and relaunched before this meeting. Earlier meetings on 15 Jul on this same install produced audio + transcripts fine.

## 3. Audio path architecture (as-built)

Understanding the loss requires knowing that **all durable audio capture is Python-side**; Swift keeps no fallback copy.

1. **Swift taps AVAudioEngine.** The mic tap converts to 16 kHz mono int16 and hands each buffer to `MicAudioForwarder.deliver(_:generation:)` (`MicAudioForwarder.swift:227`). `deliver` computes a meeting-epoch PTS, increments `frameCount`, sets `lastFrameAt`, computes the RMS level, and - if `micOutputEnabled` - calls `writer?.send(type:.audio, stream:.mic, ...)` (`MicAudioForwarder.swift:249-253`). System audio goes through `CaptureEngine` to the same writer.
2. **The writer is a pipe, not a file.** `FramedWriter.send` enqueues onto a serial `writeQueue`; `writeFrame` does `handle.write(contentsOf:)` into the child process's **stdin pipe** (`BackendProcess.swift:157-190`). There is no shared memory and no Swift-side WAV. `handle` is `backend.stdin` = `stdinPipe.fileHandleForWriting` (`BackendProcess.swift:22`, `AppModel.swift:2305`).
3. **The Python child is the only thing that writes `audio/*.wav`.** On `MSG_MEETING_START` the backend calls `open_stream_writer` for both streams (`muesli_backend.py:834-843`), which does `wave.open(path,"wb")` + `open(pcm,"wb")` (`muesli_backend.py:124-135`) - creating `system.wav`, `mic.wav`, `system.pcm`, `mic.pcm` on disk **immediately, before any audio frame**.
4. **WAV/PCM are written incrementally, per frame.** Each `MSG_AUDIO` calls `write_aligned_audio` (`muesli_backend.py:847-877`), which does `writer.wav.writeframes(payload)` + `writer.pcm.write(payload)` + **`writer.pcm.flush()` every frame** (`muesli_backend.py:245-247`). There is no "buffer in memory, flush at stop" stage. `--keep-wav` (set) only affects whether the finished WAVs are unlinked at the very end of `main()` (`muesli_backend.py:969-973`), which never ran here.
5. **Live ASR is driven off bytes written.** `LiveProcessor` runs per stream (`muesli_backend.py:485`); `_maybe_process` reads a snapshot of the `.pcm` file size (`muesli_backend.py:539-564`) and only runs ASR once enough new bytes have accumulated. Zero bytes on disk => it returns `False` forever and never invokes the model.

**Why `--keep-wav` produced nothing:** the WAVs are created in step 3, on receipt of `MSG_MEETING_START`. That message was never processed by the child, so the files were never created; `--keep-wav`'s delete-suppression at end-of-`main` is irrelevant when `main`'s read loop never advanced.

## 4. Root cause - verdict: **Hypothesis B** (Swift->Python handoff never functioned)

The task posed two hypotheses:
- **(A)** capture worked; the flush was killed at Stop (SIGKILL destroyed an in-memory buffer a graceful path would have saved).
- **(B)** the Swift->Python audio handoff was broken from the start - the backend never consumed a frame - which explains empty WAV **and** zero ASR simultaneously, with the healthy heartbeats reflecting only the Swift-side tap.

**The evidence is B, unambiguously.** Confidence-stratified so the certain parts are not confused with the inferred trigger:

### Tier 1 - proven from artifacts
- **The backend consumed no frame.** `open_stream_writer` creates the WAV+PCM files on `MSG_MEETING_START`, before any audio (`muesli_backend.py:834-843`, :124-135). The `audio/` folder is **empty**. Therefore the child never processed even the start message.
- **Zero Python output.** `MSG_MEETING_START` emits `{"type":"status","message":"meeting_started"}` (`muesli_backend.py:845`); status and stderr lines are relayed into backend.log by Swift (`AppModel.swift:675-694` - status/error only; `meter` events are deliberately **not** logged there, so their absence from backend.log alone proves nothing). The decisive artifact is stronger: **Swift appends every backend stdout line to `transcript_events.jsonl` before interpreting it** (`AppModel.swift:663-664`), and that file is **0 bytes**. The child emitted nothing at all - no status, no meters, no stderr traceback.
- **The child was alive, not crashed, at Stop.** `waitForExit` timed out (`Backend did not exit...`, backend.log:734) and `backend.onExit` never logged a `Backend exited with status N` line. A crash would have exited (status returned) and/or dumped a traceback on stderr. Neither happened -> the process was **running but not making progress**.
- **All durable capture is Python-side; Swift retains no fallback.** `deliver` forwards each buffer to the pipe and drops its reference; the forwarder keeps only a small `pendingMicAudio` ring (cap 200, `MicAudioForwarder.swift:79`) for the tap->enable window, not a meeting buffer. So the 26 minutes were thrown at a pipe nobody read and are **unrecoverable** - not sitting in any buffer a graceful stop could have flushed. This directly **refutes A**: there was no captured audio in the backend to flush, and the per-frame `pcm.flush()` (`muesli_backend.py:247`) means even a mid-meeting kill could only ever lose sub-second tails, never a whole meeting.

### Tier 2 - strong code inference
- **Alive-but-silent = wedged before or at the first read-loop iteration.** The read loop (`muesli_backend.py:806`) begins immediately after the (cheap) `StdoutWriter`/`LiveProcessor` thread starts. The only heavy synchronous work that happens *before* the loop is **the module-level import chain**: `muesli_backend.py:22` imports `.audio` (pulling in numpy/soundfile), then `:23` does `from .asr import ASRModel`, and `asr.py:11` does `from parakeet_mlx import from_pretrained` at module scope, which pulls in MLX/Metal. A wedge anywhere in that chain matches every observed symptom (no files, no output, process alive); **parakeet_mlx/MLX is the most likely link** (heaviest, touches Metal), but numpy/soundfile are inside the same proven envelope and any repro instrumentation should cover the whole chain. (Model *weights* load lazily per chunk in `_ensure_loaded`, `asr.py:62-75`, so the wedge is import-time, not weight loading. Caveat: a release build is equally silent whether wedged in import or blocked waiting at the first read - "zero Python lines" alone cannot distinguish these; what places the wedge *before* the read loop is the empty `audio/` folder despite bytes provably entering the pipe, since a reading child would have consumed `meeting_start` within milliseconds.)

### Tier 3 - plausible, unproven (suspected trigger)
- **The morning `pkill -9` -> bad MLX/Metal or leaked POSIX resource -> this launch's `import parakeet_mlx`/`import mlx` hung.** A hard SIGKILL of the previous Python process could conceivably leave GPU/Metal driver state or a named semaphore in a state that blocks the next process's MLX init. This fits "15 Jul worked, first launch after the morning `pkill -9` did not," but there is no direct artifact for it (no timestamps, no Python stderr), and ordinary process-local state (locks, globals, pipes, fds, queues) cannot survive SIGKILL - each meeting gets a fresh Process/pipe/writer (`AppModel.swift:2258-2305`) and the ASR cache is process-local (`asr.py:14`). Treat the pkill as a **weak temporal clue, not a root cause**: do not place it in the causal chain unless a reproduction (`pkill -9` the backend mid-import, relaunch, watch for a hung import with the whole import chain instrumented) or a live stack sample (`sample`/spindump of the wedged PID) confirms it.

### The Bose output-change at Stop is coincidental, not causal
The `listener.*` storm and the MacBook Pro Speakers -> Bose QC35 II output flip happen at backend.log:722-731, **after** `engine.stop` (:717), on the home screen (`screen=start`), with capture already torn down (`isCapturing=false`, `boundID=0`, `willRestart=false`). The data was already 100% lost by then - the `audio/` folder had been empty for 26 minutes. The output-device change did not cause the loss and did not cause the backend to wedge; it merely coincided with the user putting headphones on at Stop. The task's leading hypothesis (a stop-time output-device-change path) does not hold for this incident.

## 5. Why the 8 Jul fix didn't cover this

The 8 Jul fix (`804e96b`, `ad57496`) addressed a **meeting-anchored monotonic mic PTS** so the backend's `write_aligned_audio` stops silently dropping mic frames after mid-recording device churn, plus added loud drop accounting (`_log_and_count_drop`, `muesli_backend.py:160-196`). Every part of that fix lives **downstream of a functioning Swift->Python pipe**:

- It operates *inside* `write_aligned_audio` - code that only runs once a frame has been read from stdin and dispatched (`muesli_backend.py:847-877`). Here, `write_aligned_audio` was never called once.
- The `MicAudioForwarder` epoch/PTS machinery (`beginMeeting`/`beginGeneration`, `MicAudioForwarder.swift:123-168`) governs the *value* stamped on frames that reach the pipe. With zero frames consumed, PTS is moot.
- The 8 Jul incident was mid-recording device churn *while the backend was healthy and writing*; this incident is a backend that never became healthy. Different failure class entirely: 8 Jul = "alignment drops frames"; 16 Jul = "no pipe consumer exists."

So the 8 Jul fix is correct and unrelated. It cannot see, let alone recover, a backend that never entered its read loop.

## 6. Why live ASR was silent all meeting

Not a VAD/threshold/warm-up gate. `LiveProcessor._maybe_process` snapshots the `.pcm` file size and returns `False` whenever the writer is absent or the file is empty (`muesli_backend.py:562-564`), and `notify_duration` only fires on bytes actually written (`muesli_backend.py:864-877`). With the backend wedged before `open_stream_writer`, there was no writer and no `.pcm` file, so the live path never had anything to process - it never reached the ASR model at all. **Zero-ASR and empty-WAV are the same root cause, not two independent faults.** This is itself strong confirmation of B: a VAD-gated silence would still have produced `meeting_started`, `.wav`/`.pcm` files, and `meter` lines. None exist.

On `frames=` in the heartbeats: it counts frames the Swift tap **delivered to `MicAudioForwarder`** (`frameCount++` in `deliver`, `MicAudioForwarder.swift:249`; heartbeat reads `snapshot().frameCount`), **not** frames confirmed consumed by Python. So the climbing `frames` counter is fully consistent with a dead pipe consumer. On `screen=start` vs `screen=session`: `session` = the live recording screen; `start` = the home screen. The `screen=start` `ui.storm` lines appear only *after* `engine.stop`, i.e. the app navigated home post-stop - not a second recording.

## 7. The kill chain - was anything recoverable at "terminating"?

No. At `terminate()` the recoverable state was: ~64 KB in the OS stdin pipe buffer (~2 s of audio) plus whatever had backed up on Swift's `writeQueue` in memory - and even those were never going to be written, because the consumer was wedged. The 26 minutes were never buffered anywhere. A graceful stop would have saved nothing extra; SIGTERM destroyed nothing that a clean exit would have preserved. (Note: `process.terminate()` is SIGTERM, not SIGKILL.)

There is a secondary mechanism worth recording: because Python was not reading stdin, the ~64 KB pipe filled within ~2 s and `FramedWriter.writeFrame`'s `handle.write` **blocked** (it does not throw) on the serial `writeQueue` (`BackendProcess.swift:180-190`). A blocked write is not an error, so `onWriteError` -> `handleBackendWriteError` (`AppModel.swift:649-655`) never fired - that handler runs only on a *thrown* write error (e.g. EPIPE when the reader has died); a reader that is *alive but not reading* produces no exception at all, just an indefinitely blocked write on the background serial queue, invisible to the UI. It also means `closeStdinAfterDraining` / `MSG_MEETING_STOP` (queued behind the blocked write, `AppModel.swift:2550-2551`) could never drain to the child - which is a second reason the child "did not exit after stop." Scale check: post-fill frames pile up as retained payloads in queued work items - roughly 100 MB of RAM over 26 minutes at 16 kHz mono int16 - large enough to matter, small enough to be crash-free and unnoticed, which is exactly what happened.

## 8. Recommendations (ranked, with effort)

The through-line: **one child process holds 100% of durable capture, with no capture-side fallback and no fast liveness signal.** Fix that structural fragility, don't just re-patch alignment.

1. **Swift-side raw sink independent of the backend (highest value).** Have the mic forwarder and system-audio path *also* append their int16 PCM to a local `mic.raw`/`system.raw` in the meeting folder, in parallel with sending to the pipe, closed and header-wrapped to WAV on stop (or recovered on next launch like `OrphanedMeetingRecovery`). Then a wedged/crashed/never-started backend costs the *transcript*, never the *audio* - `reprocess.py` can rebuild everything from the raw files. NB the fix is Swift-side: Python already writes per-frame with flush (`muesli_backend.py:245-247`), so this is *not* "incremental WAV writing in the backend" - that already exists and is not where the loss occurred. **Effort: M** (new sink + close/recover wiring; reuses existing WAV-header code).

2. **Writequeue-backpressure detector = earliest possible alarm.** Track completion of `FramedWriter` writes; if writes stop completing for N seconds (pipe full because the reader is alive-but-not-reading), surface a visible "backend not consuming audio" warning and abort/restart the meeting. This exact signature (full pipe, blocked `handle.write`, no exception) was present within ~2-3 s of t=0 here yet nothing noticed, because `handleBackendWriteError` (`AppModel.swift:649`) fires only on a *thrown* error and a blocked write never throws. **Effort: S-M.**

3. **Backend-readiness handshake before "recording."** Do not report the meeting as live until the child has emitted `{"type":"status","message":"meeting_started"}` (`muesli_backend.py:845`) in response to `MSG_MEETING_START`. If it hasn't within a few seconds, treat start as failed and tear down (reusing `teardownFailedMeetingStart`, `AppModel.swift:2318`). This turns a silent 26-minute loss into a clean "couldn't start recording" at second ~3. **Effort: S.**

4. **Liveness watchdog on ASR/bytes, alarming DURING the meeting.** If mic frames are flowing on the Swift side (`frameCount` advancing) but the backend has reported zero `meeting_started`/`meter`/segment activity for N seconds, raise a visible warning. The zero-transcript-with-healthy-meter signature was visible from minute 1; a DURING-meeting alarm (vs the current after-the-fact log read) would have saved this meeting. Pairs naturally with #2/#3. **Effort: M.**

5. **Move the heavy import off the pre-read-loop path / make it observable.** Emit a stdout status line the instant `main()` is entered and again once imports complete, and/or defer `import parakeet_mlx` until first `_ensure_loaded`. Then an import hang is visible in the log and does not silently block the read loop from opening the WAV files. **Effort: S** (import move is one line; guard against breaking the module-level `from parakeet_mlx import from_pretrained` at `asr.py:11`).

6. **Harden stop against a wedged child.** `finalizeStoppedMeeting` waits 120 s then SIGTERM (`AppModel.swift:2634-2642`); a wedged child ignores SIGTERM too. Add an escalation to SIGKILL after a short grace, and force-close stdin directly (not only via the drainable `writeQueue`, which can itself be blocked) so the wait can't hang on a full pipe. **Effort: S.**

7. **Wall-clock timestamps on every backend.log line** (outstanding since 6 Jul and 8 Jul). This reconstruction again had to be inferred from `meeting.json` wall times + heartbeat cadence. **Effort: S.**

Suggested order: **3 + 2** (cheap, would have caught this at t~3s), then **1** (the durability backstop that makes the whole class survivable), then **4/6/5/7**.

## 9. Verification (16 Jul 2026)

This RCA was independently checked twice before being finalised:

- **Adversarial line-level verification** (`VERIFICATION-fable.md`): every load-bearing claim checked against source at file:line. Verdict: **UPHELD WITH CORRECTIONS** - all 8 claims confirmed, including the critical one that `--live-asr-only` does not change file-writing behaviour (so the empty `audio/` folder retains its evidentiary weight). Four text corrections were required and have been applied above: (1) the meter-relay-into-backend.log claim was wrong - replaced with the stronger 0-byte `transcript_events.jsonl` evidence; (2) heartbeat count arithmetic (~699 heartbeats, not ~14484); (3) "only catches EPIPE" reworded to "fires only on a thrown error"; (4) the wedge restated as the full pre-read import chain (numpy/soundfile/parakeet_mlx) with parakeet_mlx most likely. It also quantified the blocked-pipe backlog (~100 MB RAM over 26 min) and confirmed the spawn-failure / crash-on-start / path-quoting / permissions alternatives are all excluded by the artifacts.
- **Blind independent RCA, GPT-5 via Codex CLI** (`VERIFICATION-gpt5-blind.md`): given the evidence and repo but forbidden from reading this document, GPT-5 independently reached the same verdict (B), the same Bose-coincidental finding, the same zero-ASR-same-cause conclusion, and materially the same top-3 fixes. Its stricter framing of the morning `pkill -9` (weak temporal clue, not causal without repro) has been adopted in Tier 3. It additionally surfaced two secondary defects not in the original draft, recorded here:
  - **`meeting.json` "completed" is unconditional** - finalisation computes duration from wall-clock and sets `.completed` even with zero segments (`AppModel.swift:2904-2917`), which is exactly why this lost meeting presents as a successfully completed one. A "completed-but-empty" status (or refusing `.completed` when `segment_count==0` and `audio/` is empty) would make this failure class visible in the meeting list.
  - **Startup ordering:** mic forwarding is enabled as soon as the engine starts (`AppModel.swift:1289`) but `meeting_start` is enqueued later (`AppModel.swift:2371`), so a healthy backend can receive (and discard) audio frames before its writers exist. Harmless today, but the readiness handshake (rec #3) should also fix the ordering.

Net: the root-cause verdict, the 8-Jul-fix analysis, the zero-ASR explanation, and the recommendations survived both reviews unchanged; the corrections were evidentiary detail, not conclusions.
