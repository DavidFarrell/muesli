# Exact observed byte-edit evidence

`ByteEditEvidence` is a pure native verifier for a raw/official note pair. It proves only that the recorded edits reproduce the observed official UTF-8 bytes and that both inputs match their recorded lengths and SHA-256 hashes. It does not approve redaction choices, consent, speaker attribution, completeness of a note, or source cleanup. No archive entry point or external skill is changed.

Schema 1 has `evidence_kind: "observed_byte_transformation"`, `raw` and `official` fingerprints (`bytes`, `sha256`), and `edits`. Each edit contains `start_byte`, `end_byte` and canonical `replacement_base64`. Ranges are half-open offsets in the original raw UTF-8 bytes. They must fall on code-point boundaries and occur in increasing original order without overlap or repeated starts. Replacements must be valid UTF-8. An empty range inserts; an empty replacement cuts. Consent-related cuts and replacement notes use the same representation. Every unedited byte, including line endings and Unicode normalization, remains unchanged.

Limits are 8 MiB per input and total replacement bytes, 4,096 edits, and 16 MiB encoded manifest. Decoding rejects unknown/missing fields, malformed fingerprints, noncanonical base64 and unsupported versions/purpose. Validation checks actual input hashes, reconstructs within the official-size bound and compares complete bytes and hash. Call `ByteEditEvidence.decode(data)` then `validate(raw: actualRawBytes, official: actualOfficialBytes)`. The future caller must bound and read actual files under its retained ownership; this API performs no file I/O or actor handoff.

The Merge-owned local `scripts/generate-byte-edit-evidence.py --raw <path> --official <path>` reads bounded regular-file snapshots and emits JSON only after successful generation. It never modifies notes or calls the shared redaction skill. It emits zero edits for identical notes, otherwise one observed changed span after their common Unicode prefix/suffix. This linear algorithm includes every difference without claiming a semantic decomposition; unchanged text between separate edits may lie within the span. Native verification also accepts multiple exact edits from a future producer that retains individual edit decisions. The generator writes stdout; its future owning caller must publish that evidence atomically and durably. Generator success alone does not prove durable evidence publication.

Tests use synthetic text only, including actual generator-to-native interoperability. They cover UTF-8 byte boundaries and invalid sequences, consent replacements, inserts/cuts, adjacent edits, ordering/overlap, stale hashes and lengths, omitted changes, unchanged CRLF and composed/decomposed Unicode, input/replacement/manifest bounds, canonical encoding, source read mutation, and rejection of symlinks/FIFOs. No client note, external skill, recording or Trash operation is touched.
