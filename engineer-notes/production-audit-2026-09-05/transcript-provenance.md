# Transcript provenance and recoverable replacement

Transcript records retain the original `speaker_id`, `stream`, and optional `source_session_id`. A name is stored against an encoded tuple of all three fields. Legacy bare name keys can name only records without a source ID. Replayed speaker events use the source and stream on each known-speaker entry, and machine labels do not overwrite reviewed names. Partials, overlap replacement, and echo comparisons are restricted to the same source.

The viewer and speaker editor use scoped keys. Speaker identification accepts exact keys and does not infer identity from a numeric label, microphone stream, name uniqueness, or result order. Its scoped prompt treats images without verified source/time association as insufficient evidence for assigning a turn. Proposals still require the existing user review. Raw IDs and source IDs remain in JSONL; text includes source IDs and display names. Batch `transcript_sources.json` preserves even silent source inventory. A later save without complete inventory replaces it with explicit `null`, avoiding stale inventory after resume; capture metadata and source manifests remain authoritative.

`TranscriptReplacement` prepares text, JSONL, source inventory, and meeting metadata before disk mutation. It preserves the prior capture status: inference cannot certify capture completeness. `TranscriptModel.applyReplacement` commits the files before publishing any model changes. A failed Replace keeps the prior UI and pending result, with a Retry saving action.

`TranscriptPersistenceStore` stages verified and synchronized new files and original backups in `.transcript-transaction`. A durable prepared journal precedes changes to canonical files; a committed journal follows their directory synchronization. Failure restores the old snapshot. If restoration also fails, it throws an explicit recovery error and retains the journal and originals. Recovery is idempotent: prepared means restore old, committed means keep the canonical snapshot. A successful rollback or canonical-untouched staging failure durably writes this keep-canonical marker before cleanup; a crash during recursive backup deletion cannot leave a prepared journal depending on a missing backup. The same resolution happens after successful recovery. Viewer loading recovers and reads on an independent owner; older synchronous metadata callers refuse busy or unresolved folders without performing recovery or waiting. External readers must also treat a remaining prepared journal as unresolved and must not consume a mixture of canonical files. This is a recoverable multi-file transaction, not simultaneous visibility to unrelated external readers during replacement.

The shared finalizer API is `TranscriptPersistenceStore.shared.start(in:onCompletion:operation:)`. Its Sendable closure runs on a utility worker after automatic recovery, receives a Context with `readMetadata()`, `readData(named:)`, and `commit(files:)`, and can prepare finalized metadata plus `TranscriptReplacement.files(segments:text:metadata:sources:)` there. Short registry admission is per folder, with at most eight concurrent owners and no lock held during I/O. `Operation.wait(timeoutSeconds:)` returns completed(output), failed(error), timedOut, or cancelled; `value(timeoutSeconds:)` is the throwing convenience. Deadline/cancellation ends only the wait. The worker owns the folder until actual completion, and its optional terminal callback runs independently even when recovery fails before the closure. Batch retries retain the same operation after a timeout, and UI publication validates the viewer generation. Speaker edits are refused while the displayed save is unresolved. The root finalizer integration owns adoption and must not mark completion after a failure. This slice leaves its overlapping legacy save call site for that integration.

Validation uses synthetic records only: two resumed sessions with reused/permuted labels; separate stream identities; legacy-name isolation; partial/echo boundaries; source-bearing speaker events; disk staging, metadata replacement, late replacement and journal failure; rollback failure followed by recovery; successful persisted inventory with a silent source; invalid timestamp rejection before mutation. Additional tests stall an actual disk owner while MainActor remains responsive, keep another folder readable, retain admission after timeout, observe late completion without rewriting, fence a retired viewer, finish commits/callbacks while MainActor is deliberately blocked, release admission after recovery failure, and remove a backup during interrupted resolved cleanup. Full Swift suite: 219 tests passed. Release app build passed. No capture hardware or model service was exercised.
