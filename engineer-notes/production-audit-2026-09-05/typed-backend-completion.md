# Typed backend completion — isolated preparation

This slice starts from `2b4b8da3ea8479f778cab519ae7bad257ab5fc09`. It adds no XPC launch mode, app integration, entitlements, installation or permission UI. The legacy `Process` initializer and transport remain in use.

`BackendCompletionEvidence` lives beside `BackendProcess` so its constructors can be `fileprivate`. Its only active production mint is the actual `Process.terminationHandler`; stdout, result decoding, persisted receipts, wait deadlines and cancellation cannot construct it. It preserves normal exit versus signal termination. The existing batch owner obtains it only after successful output drain and actual admission/resource closure, then stores it alongside immutable event bytes and the source snapshot digest. The archive consumers use this typed route while retaining their original source-byte, processing-coverage and recovery validation. The integer exit-code API remains solely for actual legacy process observations and protocol tests; XPC must never pass an operation result through it.

The future XPC mint accepts the original `XPCBinding`, its matching bounded native `XPCReply`, and `KernelExit`. The reply contains only job ID, process-instance ID, request digest and operation status. Source identity, optional source snapshot, operation, stream and runtime/model digests come from the retained original request. Kernel evidence must match the authenticated PID and start tuple and contain both exit and exit-status observations. Successful operation status zero remains separate from actual kernel normal exit 125 or SIGKILL. Exit 126, synthetic OS exit zero, other wait statuses, missing observations and mismatched identities are rejected. The new service must distinguish failed group signalling with exit 126 before this policy is qualified; this validation alone does not prove decoder-child death.

`validateSuccessfulXPC` and `validateArchiveBinding` are testable candidate validators, not factories for native evidence. No XPC completion evidence is minted in this slice. The runner/observer integration must establish the provenance of those observations and add the sole same-file XPC mint after independent review. In particular, it must preserve reservation/ready/result/EOF/kernel-exit separation and retain ownership during uncertain or blocked startup.

`BatchSourceSnapshot.completionSHA256()` canonically hashes its ordered source/session inventory, source byte fingerprints, physical folder/access-lock identity and selected streams. Display names are excluded. A future batch XPC request must retain this digest from the original snapshot; automatic archive evidence additionally requires reprocess/both and the exact same physical source and snapshot. Live/preflight may omit this digest but cannot qualify automatic archiving.
